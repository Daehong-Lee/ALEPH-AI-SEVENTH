# 플랜두씨 다이어리 2 — 인증을 붙이고, 어떻게 붙였는지 설명하기

Diary 2는 Diary 1과 **별도의 Supabase 프로젝트/DB**를 전제로 한다. Diary 1의 테이블을 마이그레이션하거나 기존 공개 데이터를 가져오지 않는다.

## 1. 무엇으로 붙였나

- 인증 방식: 인증 서비스
- 서비스: **Supabase Auth**
- 클라이언트: `@supabase/supabase-js@2` CDN
- 인증 방식: 이메일 + 비밀번호
- 데이터 권한: Supabase PostgreSQL RLS
- Diary 2 테이블 접두사: `d2_`

Supabase Auth가 비밀번호 저장과 검증을 담당한다. 현재 Supabase 문서에 따르면 비밀번호는 bcrypt로 해시되고 랜덤 salt가 사용되며, `auth.users.encrypted_password`에는 원문이 아니라 해시가 저장된다.

## 2. 왜 Supabase Auth를 골랐나

기존 다이어리가 Supabase Database를 사용하므로 Auth와 RLS를 같은 서비스에서 연결하면 로그인 사용자의 `auth.uid()`를 DB의 `user_id`와 직접 비교할 수 있다. 비밀번호 해시와 JWT 발급/갱신을 직접 구현하지 않는 것도 중요한 이유다.

검토했지만 선택하지 않은 방법: 직접 인증 서버 구현.

선택하지 않은 이유: 비밀번호 저장, 세션 발급/갱신/폐기, 로그인 오류 처리 등을 직접 구현해야 하므로 인증 구현 자체의 위험과 유지 범위가 커진다.

## 3. 어디를 어떻게 고쳤나

### 가입
`index.html`의 가입 화면 → `app.js: signUp()` → `sb.auth.signUp({ email, password })`.

### 로그인
`index.html`의 로그인 화면 → `app.js: signIn()` → `sb.auth.signInWithPassword({ email, password })`.

### 로그아웃
`app.js: signOut()` → `sb.auth.signOut()`.

JavaScript SDK의 기본 sign-out scope는 `global`이며 모든 활성 세션을 종료한다. Supabase 문서상 sign-out으로 세션은 제거되지만 이미 발급된 access JWT는 만료 전까지 유효할 수 있으므로, Diary 2는 추가로 DB RLS에서 JWT의 `session_id`와 `auth.sessions`를 대조한다.

### 자료 조회
`app.js: loadAll()` → `d2_*` 테이블 → RLS.

### 자료 저장/수정/삭제
`app.js` CRUD 함수 → `d2_*` 테이블 → `auth.uid() = user_id` + 활성 세션 검사.

### 완료 중복 방지
`app.js: completeTask()` → `d2_complete_task_once()` RPC → `d2_task_completions.task_id UNIQUE`.

### 계정 삭제
`app.js: deleteAccount()` → `d2_delete_my_account()` → `auth.users` 삭제 → `d2_*`의 `ON DELETE CASCADE`로 계정 자료 삭제.

### 기존 자료 이전
**없다.** Diary 2는 신규 DB이므로 Diary 1의 데이터를 자동으로 가져오지 않는다.

## 4. Diary 2 DB 구조

| 테이블 | 역할 |
|---|---|
| `d2_profiles` | Auth 사용자와 연결되는 프로필 |
| `d2_plans` | 계획 |
| `d2_plan_versions` | 계획 수정 전 값 |
| `d2_tasks` | 할 일 |
| `d2_task_completions` | 완료 기록, `task_id` UNIQUE |
| `d2_execution_logs` | 실제 실행 시간/막힘 기록 |
| `d2_review_notes` | 회고 메모 |

모든 사용자 데이터 테이블에는 `user_id → auth.users.id`가 있고 RLS가 `auth.uid() = user_id`를 확인한다. 할 일/실행 기록은 부모 계획/할 일의 소유권도 함께 확인한다.

## 5. 비밀번호 처리

선택한 방식: **bcrypt (Supabase Auth가 처리)**.

비밀번호를 앱의 공개 테이블에 저장하지 않는다. Supabase Auth가 해시와 salt를 관리한다.

검증할 때는 비밀번호 원문이나 토큰을 기록하지 않는다. 예를 들어 SQL Editor에서 해시가 존재하는지만 확인할 수 있다.

```sql
select id, email, encrypted_password
from auth.users
order by created_at;
```

동일 비밀번호로 만든 두 계정의 해시가 서로 다른지 확인할 수 있지만, 제출물에는 해시 전체를 그대로 공개하지 않는다.

## 10. 짧은 확인 방법 4줄

① 어디로 가나요: 배포 주소를 새 시크릿 창에서 엽니다.
② 세 단계 안에 무엇을 하나요: 회원가입/로그인 → 계획 → 할 일 또는 실행 기록으로 이동합니다.
③ 무엇이 보이면 통과인가요: 로그인 전에는 다이어리 자료 화면이 열리지 않고 로그인 후에는 내 자료만 보입니다.
④ 안 될 때는 무엇이 보이나요: 실제 Supabase 응답과 RLS 오류를 그대로 확인합니다.

## 11. AI와 내 판단 3줄

① AI에게 맡긴 일: Supabase Auth 연결, `d2_*` 데이터 모델, RLS 정책, 세션 폐기 검사 구조를 구현했다.
② 내가 직접 판단한 일: Diary 1을 보존하기 위해 Diary 2를 별도 DB로 만들고, Diary 1 자료를 자동 이전하지 않는 것으로 결정했다.
③ AI 말을 따르지 않은 일: 실제 요청/응답, 5일 기록, 상태 코드는 AI가 추측하지 않고 사용자가 직접 확인한 값만 제출한다.
